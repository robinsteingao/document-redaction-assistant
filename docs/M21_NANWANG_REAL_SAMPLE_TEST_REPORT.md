## 1. 核心结论

南网真实样本暴露出两个必须进入 M22 的问题：第一，默认 PDF OCR 批处理在真实资料规模下会超时，用户侧看不到进度，也拿不到部分成果；第二，旧 `.doc` 文件在当前 M21 中仍是 `unsupported_format:.doc`，与产品目标中的 DOC 支持不一致。

因此，M21 当前可作为内部验证包继续使用，但不适合直接进入更大范围真实客户测试。下一步应优先补“文件选择/批处理队列/进度/失败续跑/DOC 转换”这些真实资料处理能力，而不是继续扩展外围包装。

## 3. 测试过程

### 3.1 默认配置处理 45 个真实样本副本

方式：启动 M21 发布包本地服务后，通过 `/build-package` 提交 45 个副本文件。

输入：

- DOCX：3
- DOC：6
- PDF：36
- 总大小：33.86 MB

结果：

- 运行超过 20 分钟未返回。
- 请求进程超时。
- 目标输出目录 `generated\nanwang_real_sample_output` 未创建。

判断：默认配置下，真实样本批处理没有达到用户可接受状态。即使底层仍在 OCR，前端用户看到的也会是长时间无反馈，且无部分输出、无失败定位、无恢复机制。

### 3.2 DOC/DOCX 单独探针

方式：使用 M21 发布包 CLI 处理 3 个 DOCX + 6 个 DOC。

结果：

```text

```

输出：

- `redaction_upload_package.json`
- `local_mapping.private.json`
- `review_workspace.html`
- `sandbox_import_package.json`

统计：

```json
{
  "manifest_count": 9,
  "block_count": 303,
  "field_stats": {
    "total_fields": 10,
    "by_kind": {
      "amount": 5,
```

结论：

- 3 个 DOCX 可以解析并生成文本块。
- 6 个 DOC 全部为 `parser_status=unsupported`，警告为 `unsupported_format:.doc`。
- 当前产品实际支持与目标支持不一致：用户看到“支持 DOC”时会期待旧 Word 文件可处理，但 M21 实际不能处理。

- 真实目录中 PDF 数量达到 308 个，不能依赖一次性同步请求处理。

### 3.4 36 个 PDF 单页 OCR 性能探针

方式：仅为诊断性能，将 `DRA_OCR_MAX_PAGES=1`，处理副本中的 36 个 PDF。

结果：

```text

```

统计：

```json
  "manifest_count": 36,
  "block_count": 36,
  "field_stats": {
    "total_fields": 19,
    "by_kind": {
      "amount": 9,
      "email": 1,
      "organization": 1,
      "patent_id": 4,
      "phone": 1,
      "project_name": 3
```

结论：

- 降低 OCR 页数后，36 个 PDF 可以完成，但仍耗时约 5 分钟。
- 这证明问题不是“PDF 完全不可处理”，而是默认同步批处理缺少规模控制。
- 单页 OCR 会牺牲识别完整性，不能作为最终默认策略，只能作为快速预览或初筛模式。

## 4. 安全与脱敏核查

本轮用本地映射表中的 `original` 字段反查上传包：

- DOC/DOCX 探针：未发现映射字段原文直接出现在上传包。
- PDF 5 文件默认 OCR：发现 `10万元`、`50万元` 等金额类片段仍可在上传包中检出。
- PDF 36 文件单页 OCR：发现 `10万元` 金额类片段仍可在上传包中检出。

金额片段保留不一定等同于安全错误，因为当前策略本来允许金额区间化以保留效益分析能力；但用户界面必须清楚说明“金额脱敏并非一律删除，可能以区间或量级形式保留”。否则客户会误以为所有金额原文都已清除。

## 5. 问题分级

### P0：默认真实样本批处理超时

45 个副本文件、33.86 MB，在默认配置下超过 20 分钟未返回且无输出。对普通用户来说，这就是“软件卡死”。

必须整改：

- 后台任务队列化。
- 前端显示逐文件进度。
- 每个文件独立产出状态。
- 允许跳过失败文件。
- 支持中断后续跑。
- 批处理完成前也写入临时 manifest，避免全部失败。

### P0：DOC 旧格式不支持

南网样本中 `.doc` 有 26 个，本次抽样 6 个全部 unsupported。客户不会区分 DOC 和 DOCX，只会认为 Word 文件打不开。

必须整改：

- 接入 LibreOffice/WPS 转换，将 `.doc` 转为 `.docx` 或文本后进入现有链路。
- 对转换失败文件给出明确原因，不应只给 `unsupported_format:.doc`。

### P1：PDF OCR 默认策略不适合大批量资料

默认每个 PDF 最多 OCR 5 页，单个小批次 5 个 PDF 即耗时约 70 秒。308 个 PDF 全量处理不可接受。

必须整改：

- 提供“快速预览模式”和“完整 OCR 模式”。
- 默认先抽首页或前 1-2 页识别，生成文件级风险和内容预览。
- 用户确认后再对重点文件执行完整 OCR。

### P1：金额脱敏策略需要界面解释

金额既是敏感字段，又是效益分析必要字段。当前区间化策略合理，但必须让用户理解“保留量级”与“泄露原值”的边界。

必须整改：

- 字段复核页显示金额策略：保留原值、区间化、完全隐藏。
- 默认推荐区间化。
- 明确提示完全隐藏会影响效益分析。

## 6. 结论

南网真实样本测试把 M21 的产品边界拉清楚了：核心解析、OCR、脱敏包生成链路是存在的，但真实客户资料不是几十 KB 的样例文件，而是多层目录、旧 DOC、扫描 PDF、成果附件和大量证明材料。当前 M21 缺少面向真实资料规模的任务管理能力。

M22 的目标应调整为：不是继续证明“能生成包”，而是让真实资料批处理“可等待、可观察、可恢复、可解释”。
